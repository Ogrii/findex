# findex — Лаба 1. Ітератори, генератори та ваш корпус

`findex` — пошукова система, яку я будую за семестр по одній лабі. Ця лаба — вхідна частина: **лінивий** потік
документів, **потоковий** токенізатор і статистика корпусу за один прохід з вимірюванням пам'яті.

## Корпус

**Документація CPython + усі PEP** (reStructuredText), бо шукати по документації Python — корисно саме для цього курсу.

| Частина | Файлів `.rst` | Звідки |
| --- | ---: | --- |
| `data/cpython-docs/` | 560 | `python/cpython`, тека `Doc/` |
| `data/peps/` | 765 | `python/peps`, тека `peps/` |

Версії зафіксовано в [`corpus-sources.lock`](corpus-sources.lock) (хеші комітів), тож корпус відтворюваний.
Сам `data/` у `.gitignore` — у репозиторій він не потрапляє.

## Швидкий старт

```bash
git clone <this-repo> && cd findex
uv sync                                        
uv run python scripts/fetch_corpus.py          
uv run python -m findex.stats data/          
uv run python -m findex.stats data/ --limit 100 --no-memory   
uv run python -m findex.bench data/

```

Перевірка, що це справді генератори (а не списки):

```bash

```

## Правила токенізатора

Конвеєр для одного документа: `NFC → casefold → NFC → уніфікація апострофів → re.finditer`.
Усі правила закріплені тестами в `tests/test_tokenize.py`.

| Що | Правило | Приклад |
| --- | --- | --- |
| Регістр | `casefold()`, а не `lower()` | `Straße` → `strasse` |
| Unicode | NFC (і після `casefold`, бо він може розкласти символ) | `cafe`+`◌́` → `café` |
| Апостроф усередині слова | зберігається, `’ ʼ ‘ ´` зводяться до `'` | `п’ять`, `пʼять` → `п'ять`; `don’t` → `don't` |
| Апостроф на краю слова | не входить у токен | `'quoted'` → `quoted`; `users'` → `users` |
| Присвійне `'s` | не відрізається (це справа стемінгу) | `python's` → `python's` |
| Дефіс | **роздільник** | `built-in` → `built`, `in` |
| Цифри | числа — токени; **одна крапка між цифрами** лишається | `3.12`, `1.2.3`; `3.12.` → `3.12` |
| Кома | завжди роздільник | `1,000` → `1`, `000` |
| Літери+цифри | лишаються цілими | `3rd`, `x86`, `py3` |
| Підкреслення | символ слова, але обрізається по краях | `snake_case` цілий; `__init__` → `init` |
| Решта (пунктуація, пробіли, емодзі) | роздільник | |

**Відомі обмеження:** писемності, що тримаються на комбінівних знаках без передскладених форм (деванагарі, тайська),
рвуться по цих знаках; CJK дає довгі суцільні токени. Для цього є stretch-варіант із модулем `regex` (`\p{L}`).
Складних токенів із `.` між літерами (`os.path`) немає: крапка там — роздільник.

## Вимірювання: eager проти lazy

Той самий корпус (1,325 документів, 3,899,145 токенів), однакові результати (`bench` перевіряє, що обидві
версії дали ідентичну статистику). Час — медіана з 3 запусків **без** `tracemalloc`; пам'ять — окремий запуск **з**
`tracemalloc` (він суттєво гальмує, тому час із нього брати не можна).

**Машина:** Python 3.12.16, Windows AMD64, AMD Ryzen 5 7500F, 32 ГБ RAM.

| Версія | Документів | Токенів | Пікова пам'ять | Час |
| --- | ---: | ---: | ---: | ---: |
| eager (списки) | 1,325 | 3,899,145 | 236.0 MiB | 2.45 s |
| lazy (генератори) | 1,325 | 3,899,145 | 6.9 MiB | 2.60 s |

Eager використовує **у ≈34 рази більше** пікової пам'яті, а за часом версії рівні.

### Куди пішла пам'ять

У eager-версії все живе до кінця функції: спершу `list` усіх документів, потім список списків токенів.
Розбивка (оцінка через `sys.getsizeof` після завершення, у MiB):

| Складова | MiB | Пояснення |
| --- | ---: | --- |
| Тексти всіх документів | ≈ 37 | усе, що lazy тримає по одному (найбільший файл — 0,25 MiB) |
| `str`-об'єкти токенів | ≈ 171 | 3,899,145 токенів × ≈ 46 байт: кожен збіг створює **новий** `str` навіть для `the`, що зустрічається 208 тис. разів |
| Масиви вказівників у списках | ≈ 32 | 8 байт на токен |
| `Counter` (словник) | ≈ 5 | 66,306 унікальних термів; **однаковий в обох версіях** |

Сума ≈ 245 MiB, `tracemalloc` показав 235.9: частина однолітерних токенів — закешовані синглтони, окремо не виділяються.

У lazy-версії одночасно живе лише: поточний документ (+ його нормалізована копія), поточний токен і `Counter`.
Тому пік ≈ 6.9 MiB і майже не залежить від розміру корпусу (росте лише повільно зі словником), тоді як eager росте
**лінійно** з кількістю токенів. На 28 МБ це 236 проти 7 MiB; на 50 МБ різниця була б ще більшою.

Час майже однаковий: роботи стільки ж (читання, нормалізація, regex, підрахунок), генератори її не прискорюють.
Це видно і з іншого боку: з увімкненим `tracemalloc` повний прохід займає ≈ 19.5 с проти ≈ 2.6 с без нього (тому `stats` має прапорець `--no-memory`).
